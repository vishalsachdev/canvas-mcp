# Canvas MCP security review and optimization pass

Date: 2026-09-06
Branch: `codex/review-2026-09-06`
Starting revision: `43497f9`

## Scope and method

I reviewed the current branch as a hostile but legitimately authenticated user of a local or shared Canvas MCP server. The security pass came first and covered the highest-risk areas named in the brief: host file access, anonymization, code execution, bulk grading and deletion, credentials, logging, error handling, input bounds, and dependency locks. Only after writing the security list below did I begin the optimization pass.

Baseline: `uv run python -m pytest tests/ -rf -q` collected 1,478 tests and finished with **1,457 passed, 21 skipped, 2 warnings in 30.60 seconds**. The warnings were pre-existing: one un-awaited test mock and one Starlette deprecation warning.

Automated checks used as supporting evidence, not as substitutes for code review:

- `pip-audit`: no known Python vulnerabilities in the resolved environment.
- `npm audit`: 0 vulnerabilities across 75 production, development, optional, and peer dependency entries.
- Bandit: 0 high-severity results. Its two medium alerts were reviewed manually; the public bind is protected by fail-closed startup authentication checks, and the named container temp files are isolated tmpfs mount declarations rather than host temp-file creation.

## Security findings (written before the optimization pass)

### Critical

None found.

### High

#### S1. Shared-server users can write student reports and identity maps to the server's disk

- Evidence: before the fix, the affected paths were `generate_peer_review_report`, `extract_peer_review_dataset`, and `create_student_anonymization_map`. The new host-boundary checks are at `src/canvas_mcp/tools/peer_reviews.py:138`, `src/canvas_mcp/tools/peer_review_comments.py:220`, and `src/canvas_mcp/tools/admin_tools.py:312`.
- Exploit scenario: an authenticated remote instructor calls the peer-review dataset tool with its default `save_locally=True`, or calls either of the other local-save paths. The server writes raw student records to its own persistent working directory. Repeating calls with distinct names can fill shared storage; the anonymization-map path also persists the direct name/email-to-pseudonym mapping. The ordinary upload/download tools already recognize this host boundary and refuse it over HTTP, but these three paths did not.
- Fix: refuse every local export before any Canvas request or filesystem operation when the tool is running over HTTP. Keep local stdio exports available, and correct the MCP metadata so clients no longer treat filesystem-writing variants as read-only.
- Status: fixed in `735ca36`. Four regression tests prove that HTTP callers are refused before any Canvas request or file write, while local stdio use remains available.

### Medium

#### S2. A code-execution caller can exhaust host memory through unlimited output

- Evidence: `src/canvas_mcp/tools/code_execution.py:680-731` captures both pipes with `process.communicate()` and decodes the complete byte strings. The configured container memory limit constrains the child, not the parent process accumulating pipe output.
- Exploit scenario: when the optional code-execution tool is enabled, a legitimate caller prints an unbounded stream until the timeout. The Python server retains all stdout and stderr and can be killed by host memory pressure even though the container itself is limited.
- Fix: consume both streams incrementally, retain only a configured maximum, kill the child when the combined cap is exceeded, and return an explicit truncation/refusal result. This is not a safe sub-30-line change because concurrent pipe draining and process cleanup must remain deadlock-free.
- Status: recommendation; not implemented in this time box.

#### S3. Debug logging can disclose credentials embedded in a storage upload URL

- Evidence: before the fix, `upload_file_to_storage()` logged the complete Canvas-supplied `upload_url`. The corrected call is at `src/canvas_mcp/core/client.py:656`, backed by the URL sanitizer at `src/canvas_mcp/core/logging.py:73`.
- Exploit scenario: a storage backend returns a presigned upload URL with a signature or temporary credential in its query string. With request logging enabled, that credential is copied to stderr and any central log collector, allowing anyone with log access to reuse it during its validity window.
- Fix: strip user-info, query, and fragment data before a URL is logged, while retaining the scheme, host, and redacted path for diagnosis.
- Status: fixed in `afb4cc0`. The sanitizer now removes URL user-info, query strings, and fragments before logging; a focused upload test confirms that a presigned credential cannot appear in the log message.

#### S4. Normal MCP HTTP request bodies have no application-level size limit

- Evidence: `src/canvas_mcp/server.py:85-119` provides a bounded reader, but `src/canvas_mcp/server.py:311-325` applies it only to the unauthenticated approval-confirmation form. The ordinary authenticated request path at `src/canvas_mcp/server.py:329-410` passes the body through without a declared-length or streamed-byte cap.
- Exploit scenario: an authenticated user sends a very large or chunked JSON-RPC request. The downstream framework must buffer and parse it before parameter validation, consuming shared memory and CPU. Several tools also accept arbitrarily large collections or strings, increasing amplification.
- Fix: add a configurable ASGI receive limit for all MCP HTTP requests, enforce both `Content-Length` and actual streamed bytes, and return 413 before JSON parsing. This needs an integration-tested receive wrapper and is not a safe sub-30-line patch.
- Status: recommendation; not implemented in this time box.

#### S5. Announcement title regular expressions can block the event loop

- Evidence: `src/canvas_mcp/tools/discussions.py:1416-1462` applies a caller-controlled Python regular expression to Canvas-controlled titles with no time or complexity bound.
- Exploit scenario: an authenticated shared-server user supplies a catastrophic-backtracking expression and arranges a long non-matching title. The synchronous match monopolizes the event loop and delays every caller.
- Fix: replace the unbounded regex option with a timeout-capable engine and a short timeout, or retire regular-expression matching in favor of bounded literal/glob matching. This changes a public filter contract and needs focused compatibility tests.
- Status: recommendation; not implemented in this time box.

### Low

#### S6. Access-key comparison stops at the matching set entry

- Evidence: `src/canvas_mcp/server.py:123-129` says every comparison runs, but Python's `any()` stops after the first true result.
- Exploit scenario: a network attacker who already has a valid key may distinguish which internal iteration position matched through many precise timing samples. The comparison itself remains constant-time and this does not reveal characters of a high-entropy unknown key, so practical impact is low.
- Fix: OR integer results across every allowed key without short-circuiting.
- Status: not implemented; lower value than the host-write and credential-log fixes.

#### S7. The anonymization mapping cache has no bound or lifecycle isolation

- Evidence: `src/canvas_mcp/core/anonymization.py:13-14` and `src/canvas_mcp/core/anonymization.py:188-213` retain one global entry for every observed identity until an explicit clear that normal request handling does not call.
- Exploit scenario: a long-lived shared process accumulates identities from every course queried. A user with broad roster access can steadily increase memory use, and the global status count mixes activity across callers.
- Fix: remove the unnecessary value cache (the pseudonym is deterministic), or replace it with a bounded per-request/per-tenant cache and non-global statistics.
- Status: recommendation; not implemented because changing the public status statistics needs a separate design decision.

## Optimization findings

### O1. Peer-review completion analytics downloads the same roster twice

- Trace: before the change, `PeerReviewAnalyzer.get_completion_analytics()` asked `get_assignments()` to download names and then downloaded the identical roster again. One completion request therefore made four logical Canvas calls instead of three: assignment, peer reviews, roster, roster.
- Improvement: ask the helper for IDs only, download the roster once in the caller, and use that one map for reviewer and reviewee names. This preserves the response while removing one fully paginated request.
- Status: implemented in `63d2037`. The helper now requests IDs only at `src/canvas_mcp/core/peer_reviews.py:122`, and one roster supplies both reviewer and reviewee names. A call-count regression test verifies the roster is fetched exactly once.

### O2. Report generation repeats the assignment and peer-review scan

- Trace: `generate_report()` calls `get_completion_analytics()` at `src/canvas_mcp/core/peer_reviews.py:245-248`, which obtains assignment details and peer-review assignments, then calls `get_assignments()` again at lines 253-258 solely to recover `assignment_info`. After O1, this is six logical requests where three should suffice.
- Improvement: refactor a private collector to return analytics and assignment metadata together, while keeping both public method result shapes unchanged.
- Status: recommendation; broader than O1 and should follow with dedicated shape-compatibility tests.

### O3. Two common overview tools serialize independent network work

- Trace: `list_groups()` loops at `src/canvas_mcp/tools/admin_tools.py:80-96` and waits for each group's member list before starting the next. `get_course_content_overview()` similarly waits for up to ten module-item lists one by one at `src/canvas_mcp/tools/courses.py:409-415`. With ten groups/modules and 100 ms latency, the loop alone adds about one second even though the shared request semaphore already provides a safe concurrency ceiling.
- Improvement: create all independent fetch coroutines and use `asyncio.gather()`; preserve source ordering when formatting results and rely on the existing global semaphore for the configured ceiling.
- Status: recommendation; test with delayed fakes to prove overlap and unchanged ordering before changing it.

### O4. HTTP transport creates a new connection pool for every Canvas call

- Trace: in per-request HTTP mode, `make_canvas_request()` constructs and closes a new `httpx.AsyncClient` at `src/canvas_mcp/core/client.py:458-470` and `603-607`. Pagination and multi-call tools therefore repeat TCP/TLS setup for every page or endpoint, while stdio correctly reuses a client.
- Improvement: place one authenticated client in request context, reuse it for all Canvas calls made by that MCP request, and close it in middleware cleanup.
- Status: top performance recommendation; needs HTTP concurrency and credential-isolation tests before implementation.

### O5. File upload reads the entire file synchronously before sending

- Trace: `upload_file_to_storage()` opens and reads the whole file at `src/canvas_mcp/core/client.py:641-651`, then hands the in-memory bytes to `httpx`. A 100 MB upload therefore allocates roughly another 100 MB and performs blocking disk I/O on the event loop.
- Improvement: stream from an opened file object or an async producer and keep validation/TOCTOU semantics explicit; use a bounded worker thread if the HTTP library's multipart encoder remains synchronous.
- Status: recommendation; requires representative large-file measurement and failure cleanup tests.

## Test-first evidence

- Host-write boundary red: 4 tests collected, 4 failed. The tools returned student data, wrote a local export, or reached Canvas instead of refusing the HTTP call. Green: 12 related security and metadata tests passed.
- URL-secret red: the sanitizer retained `service:password`, a query token, and a fragment; the upload logger retained `X-Amz-Credential` and `X-Amz-Signature`. Green: 85 sanitizer, client, and file-tool tests passed.
- Duplicate-roster red: the new regression test observed 2 roster fetches instead of 1. Green: 140 peer-review tests passed, with 1 pre-existing warning.
- Registry correction: the focused fencing checks passed 5 tests after the metadata-aware assertion was repaired.

## Public behavior and compatibility

- Over HTTP, `generate_peer_review_report(save_to_file=True)`, `extract_peer_review_dataset(save_locally=True)`, and `create_student_anonymization_map(...)` now return a refusal instead of writing student data to the shared host. Remote dataset callers that only need returned data must explicitly use `save_locally=False`.
- The same local-save operations remain available in local stdio mode. Returned report and analytics shapes are otherwise unchanged.
- Two tools that can optionally write files are no longer advertised as read-only. This is a metadata correction and may make cautious clients ask for confirmation.
- Storage upload behavior is unchanged; only credential-bearing URL components are removed from debug logs.

## Unfinished work, in priority order

1. Cap and stream code-execution output so a caller cannot exhaust the parent server's memory (S2).
2. Enforce an application-level size limit on every MCP HTTP request before JSON parsing (S4).
3. Reuse one isolated Canvas HTTP connection pool per MCP request to remove repeated TCP/TLS setup (O4).
4. Bound announcement title matching, then address the lower-risk access-key short-circuit and anonymization-cache lifecycle (S5-S7).
5. Consolidate report collection, parallelize independent overview fetches, and stream large uploads (O2, O3, O5).
