### ⚠️ #283 — [Bug]: Create announcement tool (student-role write tool; first comment still owed)

**What they reported:** Testing as a student, they asked to create an announcement. The tool told
them it couldn't post an announcement — but posted a discussion topic instead, without asking
first. They expected a 403, not a silent discussion post.

**Root cause, verified in code — `discussions.py:1038-1106` (`create_announcement`):**
This is the exact Canvas quirk #220 already found and partially fixed. The tool POSTs to
`/courses/{id}/discussion_topics` with `is_announcement: true`. When the caller's token lacks
announcement-posting rights in that course — any ordinary student token — Canvas does **not**
reject the write. It returns `200`, silently drops `is_announcement`, and creates a regular
discussion topic instead. #220's fix (lines 1084–1101) detects this by checking whether Canvas
echoed `is_announcement` back in the response; if not, it returns `unconfirmed_write_warning(...)`
naming the discussion topic ID and telling the caller their token likely lacks permission.

That is precisely what the reporter is describing — the warning **is** firing correctly. What
they're actually flagging is a real gap the #220 fix didn't close: the permission check happens
*after* Canvas has already created the discussion topic as a side effect, not before. There is no
preflight permission check today, so a student token always leaves behind a real discussion topic
in the course before the caller ever sees the warning. Getting a clean refusal instead of a
side-effect-then-warning would need a permissions check (e.g. against `/courses/{id}/permissions`)
before the POST — unverified whether Canvas's permissions endpoint reliably reports the specific
`moderate_forum`-style right needed here; flagging as a design question, not proposing a fix.

**Sensitivity:** student role + write tool + permissions — flagged per this routine's standing
instruction to be conservative here.
