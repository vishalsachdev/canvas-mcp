- **#299 — "Feature: optional cookie-based auth for Canvas instances that don't issue API
  tokens"**, opened by **`turner-moore`, a first-time contributor**, 2026-08-17T16:23Z. No
  comments yet.

  ⚠️ **High-sensitivity: touches credential handling.** Proposes an opt-in `CANVAS_AUTH_MODE=cookie`
  mode that reads session cookies from a user-supplied JSON file (Cookie-Editor export format),
  host-filtered to the `CANVAS_API_URL` domain, sent instead of the `Authorization: Bearer` header.
  Default stays `token`; claims the change is contained to `core/config.py` (env var + path
  validation) and `core/client.py` (cookies-vs-header selection), since all ~99 tools already route
  through `make_canvas_request()`. They're asking three specific things before opening a PR: (1)
  whether you'd accept this as a contribution, (2) any preference on the env var names, (3) any
  preference on the cookie file format or where docs should live.

  This is architecturally plausible on a skim — every tool does go through one client function —
  but unverified: I have not read `core/client.py`/`core/config.py` to confirm the claimed scope,
  and a claim of "docs recommend chmod 600" is not the same as an enforced permission check. Worth
  scrutinizing whether the file-permission and host-filtering guarantees are actually enforced in
  code (not just documented) before this merges, given canvas-mcp's FERPA obligations.

  **Added after an automated review on this triage PR flagged it, and independently confirmed by
  reading `core/credentials.py`:** the proposal as written is stdio-only and doesn't say so. HTTP
  transport already carries **per-request** credentials — `RequestCredentials(api_token, api_url)`
  threaded through a `ContextVar` per request, with an explicit fail-closed guard
  (`is_http_request_active()`) specifically so a missing per-request token can never fall back to
  the server's own credentials. A single global `CANVAS_COOKIES_PATH` read from server-side disk
  has no way to plug into that per-request model: it would either silently do nothing for HTTP
  callers, or — if wired in as a naive fallback — run every HTTP caller as whoever's cookie sits on
  the server, which is a cross-tenant credential leak on the hosted deployment. This needs to be
  either explicitly scoped to stdio-only, or paired with a per-request cookie/isolation design
  before HTTP support is claimed. Folded into the draft reply below.

### New finding — `test_pii_access_logged` is time-dependent flaky on `main` (0.60% per run)

The single failure above is **not** attributable to #297, whose diff touches only `package.json`
and `package-lock.json`. Two subsequent full-suite runs on the identical head both passed, and the
test passes in isolation. Root cause, from reading the code rather than re-rolling the dice:

`tests/security/test_ferpa_compliance.py:103` asserts that a sanitized audit line leaks no raw IDs:

```python
log_data_access("GET", "/courses/123/users/456", "success")
captured = capsys.readouterr()
assert "123" not in captured.err
assert "456" not in captured.err
```

but `core/audit.py:106` stamps every event before emitting it:

```python
event["timestamp"] = datetime.now(timezone.utc).isoformat()
```

The 6-digit microsecond field (and its boundary with the seconds field) can contain `123` or `456`
by pure chance, and the assertion scans the whole stderr blob, not the sanitized `endpoint` value.
Measured over 200,000 consecutive microsecond values:

```
timestamps containing '123' or '456': 1200/200000 = 0.60%
examples: ['2026-08-18T01:46:30.491456+00:00', '2026-08-18T01:46:30.492123+00:00', ...]
```

So roughly **1 run in 167 reddens for no reason**, on `main`, on every PR, on all four Python
matrix legs independently — call it a ~2.4% chance that at least one leg of a given PR's matrix
goes red. It went unnoticed until now partly because, per CLAUDE.md, CI only started actually
running this suite in #247. The sanitizer itself is fine — this is a test-assertion defect, not a
FERPA defect: `_sanitize_endpoint()` did its job in the failing run. Suggested repair (not applied
— outside my write boundary): parse the emitted JSON and assert on `event["endpoint"]`, or drop the
`timestamp` key before the substring check. Listed under **Needs Vishal**.

### #299 — scope claim spot-verified, with two corrections

The brief flagged the "contained to `core/config.py` + `core/client.py`" claim as plausible but
unread. Read now.

**Confirmed, Python side.** There is exactly one place that builds Canvas auth headers:
`_canvas_auth_headers()` at `src/canvas_mcp/core/client.py:27-32`, called from three sites (`:353`
shared client, `:385` `canvas_authenticated_client()`, `:461` per-request client). `grep` for
`Authorization` across `src/**/*.py` returns no other construction site — the only two other hits
are prose in `config.py` docstrings. The one `httpx.AsyncClient` built without auth
(`client.py:642`) is the S3/Instructure upload path, which is deliberately unauthenticated and
routes its authenticated redirect follow-up back through `canvas_authenticated_client()`. So the
"every tool already goes through one function" premise holds for the ~99 Python tools.

**Correction 1 — there is a second auth path, in TypeScript.** `src/canvas_mcp/code_api/client.ts:90`
builds its own header:

```ts
'Authorization': `Bearer ${cfg.apiToken}`
```

That is the `execute_typescript` sandbox's Canvas client. A cookie mode confined to the two named
Python files would leave it token-only, so a cookie-mode user calling `execute_typescript` would
get failures from a path the feature never touched. Not fatal (the tool is opt-in per #178 and
disabled on hosted), but "roughly two files" is incomplete as stated and should be settled before
the PR, not during review.

**Correction 2 — superseded, and independently converged on.** I had written this up as "cookie
mode should almost certainly be stdio-only," reasoning from the per-request credentials at
`client.py:385`/`:461` and the hosted startup guard that forbids a server-side `CANVAS_API_TOKEN`.
While I was measuring, the triage agent pushed `7685d7f` to this branch covering the same gap from
`core/credentials.py`, in more depth (the `ContextVar` + `is_http_request_active()` fail-closed
design, and the cross-tenant leak if a cookie file were ever wired in as a fallback), and folded it
into the draft reply. **Its version stands; mine adds nothing.** Recording the convergence only
because two independent reads reaching the same conclusion is itself evidence the ask is right.

One small addition that survives: there is an existing pattern to copy for the guard —
the inapplicable-env-var map at `core/config.py:346-354`, which rejects `MCP_CLIENT_AUTH_MODE` and
friends with a per-variable reason string. `CANVAS_AUTH_MODE=cookie` under HTTP transport fits that
shape exactly.
