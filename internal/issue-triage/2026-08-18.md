- **#299 — "Feature: optional cookie-based auth for Canvas instances that don't issue API
  tokens"**, opened by **`turner-moore`, a first-time contributor**, 2026-08-17T16:23Z. No
  comments yet.

  ⚠️ **High-sensitivity: touches credential handling.** Proposes an opt-in `CANVAS_AUTH_MODE=cookie`
  mode that reads session cookies from a user-supplied JSON file (Cookie-Editor export format),
  host-filtered to the `CANVAS_API_URL` domain, sent instead of the `Authorization: Bearer` header.
  Default stays `token`; claims the change is contained to `core/config.py` (env var + path
  validation) and `core/client.py` (cookies-vs-header selection), since all ~99 tools already route
  through `make_canvas_request()`. They're asking three specific things before opening a PR: (1)
  whether you'd accept this as a contribution, (2) any preference on the env var names, (3) any
  preference on the cookie file format or where docs should live.

  This is architecturally plausible on a skim — every tool does go through one client function —
  but unverified: I have not read `core/client.py`/`core/config.py` to confirm the claimed scope,
  and a claim of "docs recommend chmod 600" is not the same as an enforced permission check. Worth
  scrutinizing whether the file-permission and host-filtering guarantees are actually enforced in
  code (not just documented) before this merges, given canvas-mcp's FERPA obligations.

  **Added after an automated review on this triage PR flagged it, and independently confirmed by
  reading `core/credentials.py`:** the proposal as written is stdio-only and doesn't say so. HTTP
  transport already carries **per-request** credentials — `RequestCredentials(api_token, api_url)`
  threaded through a `ContextVar` per request, with an explicit fail-closed guard
  (`is_http_request_active()`) specifically so a missing per-request token can never fall back to
  the server's own credentials. A single global `CANVAS_COOKIES_PATH` read from server-side disk
  has no way to plug into that per-request model: it would either silently do nothing for HTTP
  callers, or — if wired in as a naive fallback — run every HTTP caller as whoever's cookie sits on
  the server, which is a cross-tenant credential leak on the hosted deployment. This needs to be
  either explicitly scoped to stdio-only, or paired with a per-request cookie/isolation design
  before HTTP support is claimed. Folded into the draft reply below.

  Draft reply:
  ```
  Thanks for the detailed writeup — the SSO-only-token-page constraint hadn't occurred to me, and
  I like that this is opt-in with make_canvas_request() as the single choke point.

  Since this touches how credentials get read and transmitted, it lands as high-sensitivity here
  (FERPA-adjacent), so the review bar will be a bit higher than usual — that's not a knock on the
  idea, just flagging it up front.

  On your three questions:
  - CANVAS_AUTH_MODE / CANVAS_COOKIES_PATH both fit our existing CANVAS_* convention, no objection.
  - Cookie-Editor's JSON array format is fine, as long as we fail loudly (not silently) on a
    malformed or missing file rather than falling back to no auth.
  - Docs: a new subsection under auth setup in AGENTS.md/README, plus the var names in
    env.template.

  Two more asks beyond the three:
  - Please add tests per our TDD policy (see CLAUDE.md) — success path, malformed/missing cookie
    file, and specifically the host-filtering behavior, since that's the part most likely to leak a
    cookie to the wrong host if it ever regresses.
  - This needs to be explicitly stdio-only. We also run an HTTP transport where credentials are
    per-request (X-Canvas-Token, threaded via contextvars, fail-closed if missing) so multiple
    callers can share one server process safely. A single server-side CANVAS_COOKIES_PATH doesn't
    fit that model — it'd either no-op for HTTP callers or, if someone later wires it in as a
    fallback, run every HTTP caller as whoever's cookie is on disk. Either gate cookie mode out of
    HTTP mode explicitly (and say so in the docs), or the design needs a per-request cookie story
    before HTTP is on the table.

  Go ahead and open a PR against main from a feature/ branch — happy to take a close look.
  ```
