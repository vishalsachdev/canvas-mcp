## Addendum (2026-09-08T02:30Z) — the intermittent suite failure is identified

CI failed on this brief's own executor commit (`f58dd8e`), on a change that touches exactly one
markdown file under `internal/issue-triage/`. Chased it, and it is the sporadic single-test
failure recorded in `CLAUDE.md` under 2026-08-30 as "**Unidentified flake**" — the run that
reported `1 failed, 1456 passed` with no `-rf`, so the test name was never captured. It has a
name now.

**The test:** `tests/security/test_ferpa_compliance.py:130`,
`TestAuditLogging::test_pii_access_logged`.

**What CI saw** (`test (3.11)`, job `101916495951` — 3.12 and 3.13 passed in the same run):

```
tests/security/test_ferpa_compliance.py:130: in test_pii_access_logged
    assert "123" not in captured.err
E   assert '123' not in '{"event_typ...07+00:00"}\n'
E     '123' is contained here:
E       02:23:08.612307+00:00"}
E     ?           +++
=========== 1 failed, 1471 passed, 20 skipped, 2 warnings in 18.49s ============
```

**Root cause — a test bug, not a product bug.** The test logs a data-access event for
`/courses/123/users/456` and then asserts the raw IDs were sanitized out:

```python
log_data_access("GET", "/courses/123/users/456", "success")
captured = capsys.readouterr()
assert "data_access" in captured.err
assert "123" not in captured.err     # <-- scoped to the whole line, not the endpoint field
assert "456" not in captured.err
```

The assertion is scoped to the **entire captured stderr line**, which is a JSON audit record
carrying an ISO-8601 timestamp with microseconds. Whenever that timestamp's digits happen to
contain `123` or `456` as a substring, the assertion fails — here `...08.612307...` contains
`123` at the `.6`**`123`**`07` boundary. Nothing to do with the endpoint sanitization, which is
working; the needle is landing in the haystack's timestamp.

**Measured rate.** Sampling 200,000 realistic `datetime.isoformat()` values:

```
timestamps containing '123' or '456': 1583/200000 = 0.79%
```

≈0.79% per matrix job, so ≈3.1% that at least one of the four jobs in a CI run trips it. That
matches the observed behavior exactly: mostly invisible, occasionally one job red on an
unrelated change, always green on the re-run. It also explains why 2026-08-30's four follow-up
runs came back clean — that was luck, not evidence the failure had gone away.

**This does not change any conclusion above.** My local runs (1477/1470 passed) and the 3.12 /
3.13 jobs on this same commit are unaffected; the failure is independent of every PR reviewed
in this brief. In particular it is *not* related to correction 1 — #358's `test (3.11)` really
did pass; this is a different, later run on a different branch.

**Suggested fix (not applied — outside my write boundary):** scope the assertions to the
sanitized field rather than the raw line, e.g. parse the JSON and assert against
`record["endpoint"]`, or assert the endpoint equals its expected sanitized form
(`/courses/***/users/***`). Asserting on a parsed field also makes the test check the thing it
means to check instead of a substring of an entire log record.

Re-running CI by pushing this addendum. If it goes green, the failure was this flake and the
brief merges; if `test (3.11)` fails the same way again, that would be a real signal and I will
leave the PR open.
