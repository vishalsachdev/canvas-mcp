### #569 — "[Bug]: Trying to edit rubrics results in a new rubric being created and the old rubric disappearing" (mwhalen805, first-time reporter)

Opened 2026-11-06T15:35:02Z. No comments yet. Report: user creates a rubric for an assignment, then asks to "edit" it; since there is no edit-rubric prompt path the assistant uses, the request becomes a second `create_rubric` call. After that, the original rubric is gone from Canvas entirely (not just from the assignment), with no delete tool ever called. They're not objecting to the new-rubric-instead-of-edit behavior itself — they're asking why the old one vanishes instead of both existing side by side.

⚠️ **Flag:** this is destructive data loss in Canvas (an instructor's prior rubric and any criteria disappear) triggered by a tool that is not supposed to delete anything, so it's worth prioritizing even though it isn't a credentials/FERPA issue.

**Unverified analysis, not a confirmed root cause:** `canvas-mcp` *does* ship `update_rubric` (`src/canvas_mcp/tools/rubrics.py:1668`), a confirm-before-write tool that edits an existing rubric's criteria/ratings in place without touching its identity or associations — so if the client had called that instead of making a second `create_rubric`, this wouldn't come up. The question is why the *original* rubric disappears from Canvas once a second one is created, since neither `create_rubric` (`rubrics.py:1552`) nor anything else in this server issues a DELETE against `/rubrics`. My best guess: `create_rubric` defaults `reusable=False` (`rubrics.py:1558`) and, when given `assignment_id`, both creates the new rubric and points the assignment's rubric association at it via `build_rubric_create_form_data` (`rubrics.py:1627-1635`) — this replaces, rather than adds to, the assignment's single rubric association. Canvas itself (not this server) appears to garbage-collect a non-reusable rubric once its last association is gone, which would explain the first rubric vanishing from `list_rubrics`' `/courses/{id}/rubrics` listing (`rubrics.py:1338`) with no delete call anywhere in this codebase. This is a hypothesis about Canvas-side behavior, not something I reproduced against a live course, and I haven't confirmed what `reusable=True` would have done instead.

**Draft reply:**
```
Thanks for the clear repro steps. A few things worth untangling here:

First, there is an edit path that avoids this entirely: update_rubric replaces an existing rubric's criteria/ratings in place (with a preview + confirmation step) without creating a new rubric or touching its Canvas association. If your assistant chose to "create a new one" instead, that's a client-side tool-selection gap, not something this server can fix by itself — though I can look at whether the create_rubric description should more clearly discourage that path when an edit is meant.

Second, and this is the part I want to understand before promising a fix: nothing in canvas-mcp calls a delete endpoint on rubrics, ever — create_rubric only POSTs a new rubric and (when you give it an assignment_id) points that assignment's rubric association at the new one. My working theory is that Canvas itself removes a non-reusable rubric once it loses its last association, which would be what you're seeing as "disappearing," rather than an explicit delete from our side. Could you check, in Canvas's own course-level rubric list (not just the assignment), whether the old rubric is truly gone versus just unassociated? And do you recall whether the original rubric was created with "reusable" on or off? That will tell us whether this is a Canvas platform behavior to document/guard against, or something to reproduce more carefully on our end.
```
