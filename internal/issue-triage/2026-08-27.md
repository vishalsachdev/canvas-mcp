### ⚠️ New finding the brief and the first pass both missed — merging #317 auto-closes [issue 157]

PR #317's **first commit (`277ef8e`) ends with a `Fixes` `#157` trailer** — line-opening, with the
parenthetical "(item 2 of 4; items 1/3/4 are separate, broader changes)". The contributor's own words
say this is one item of four, so retiring [issue 157] is precisely what should *not* happen on merge.
It is live in `CLAUDE.md` Current Focus (egress is item 1, still open and explicitly "only mitigated,
not closed").

This is not a guard failure — it is the guard working as specified, and worth understanding before you
touch the merge button. Run against that commit message, the two forms disagree (output paraphrased
here on purpose, so this brief does not re-arm the very trailer it is describing):

```
scripts/check_closing_keywords.py --strict         → exit 1, warns the default branch would retire the issue
scripts/check_closing_keywords.py --git-comments   → exit 0, "deliberate trailer, allowed"
```

CI runs the second form. A line-opening keyword is treated as a deliberate trailer by design, so the
`Closing Keyword Guard` check on `277ef8e` reports **success** while the closure it waves through is
wrong. The guard cannot know the difference; only you can.

**This section tripped the guard while being written.** The first draft described the problem in prose
and `--strict` flagged six hits — a brief explaining the #172 landmine would itself have retired
[issue 157] on merge. Rewritten to break every keyword/reference pair. Worth knowing that even writing
*about* this failure mode reproduces it.

**The merge method decides the outcome:**
- *Merge commit* or *rebase* → `277ef8e`'s message lands on `main` verbatim → **the issue is retired.**
- *Squash* → GitHub's default squash body for a multi-commit PR is the **concatenation of the commit
  messages**, so the trailer comes along anyway unless you clear it out of the box → **also retired**,
  unless you edit it. The PR *body* is clean (it uses `Refs`), but the body is not what squash defaults
  to here.

So no merge method is safe by default. Either edit the squash message down to the PR body, or reopen
[issue 157] immediately after merging. This is the same mechanism that killed #172 twice; the guard
added afterward does not catch this shape.
