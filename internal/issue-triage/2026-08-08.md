### #234 ⚠️ — update_page_settings silently no-ops on "Notify users that this content has changed"
zqian asked to set the notify flag to true for a page; the tool reported success, but the checkbox in Canvas's
UI stayed unchecked.

**Unverified analysis** — `pages.py:58-59` passes `notify_of_update` straight through as
`wiki_page[notify_of_update]`, structurally identical to `published`/`front_page` (which zqian hasn't reported
as broken), and the whole payload deliberately goes as JSON, not form-encoded (comment at `pages.py:154-155`
references #207 — form-encoding a nested dict breaks Canvas with a 500, so JSON is the fix, not the bug here).
My best guess, unconfirmed, is a Canvas API quirk rather than an encoding bug: Canvas may only actually flip
that notification flag when the same request also changes the page **body** — i.e., a settings-only call with
no content edit might be silently ignored server-side, similar in shape to the `is_announcement` issue fixed in
#220 (Canvas doing less than the request implied). Also worth noting: our code never verifies the setting stuck
— it builds its success message from the PUT response without checking whether Canvas's response actually
reflects the new value, same failure class as #180/#181/#219-221.

```

way as published/front_page, which worked fine for you. My best
```
