Both are on `fastmcp==4.0.3` (the pin is `fastmcp>=4,<5`, so a lockfile-only bump to 4.1.2 clears both without touching the constraint):

- **GHSA-7xgj-8392-5q4r** — a FastMCP *server*-side authorization bypass: a configured server transform can change a tool/resource/prompt's identity, and FastMCP's direct-lookup path returned the transformed component without re-running its `AuthCheck` against the transformed identity. Affects FastMCP 3.0.0–3.4.9 and 4.0.0–4.1.1; fixed in 3.4.10/4.1.2.
- **GHSA-vqqp-x5qm-5qp4** — a FastMCP *client*-side OAuth issuer-binding leak: `ClientCredentialsOAuthProvider`/`PrivateKeyJWTOAuthProvider` don't validate that the authorization server an MCP server advertises matches the issuer the credential was configured for, so a malicious or compromised MCP server URL can receive the client secret. Affects 4.0.0–4.1.1; fixed in 4.1.2 (also needs explicit `issuer=` configuration; upgrading alone isn't sufficient).

**Exposure here, read off this repo's own source, not assumed:** a repo-wide grep for `ToolTransform`, `add_transform`, `restrict_tag`, `AuthCheck`, `ClientCredentialsOAuthProvider`, and `PrivateKeyJWTOAuthProvider` under `src/` returns nothing. This server doesn't use FastMCP's transform/component-authorization system (tool gating is this repo's own `core/tool_policy.py`, not FastMCP's `AuthCheck`), and it doesn't use FastMCP's M2M OAuth client providers to connect outbound to other MCP servers. Both advisories' attack surface appears absent from this codebase, by inspection only — I did not run either PoC against this server.
