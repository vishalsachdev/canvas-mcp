This triage PR's own CI run (head `f4aae7c`) failed the **Dependency Vulnerability Scan**. This is worth flagging on its own, separate from the rest of this brief, because it is new and affects more than this PR.

**Not caused by this PR.** The PR's only change is this one markdown file; `pyproject.toml` and `uv.lock` are byte-identical to `origin/main` (`git diff origin/main -- pyproject.toml uv.lock` is empty). The exact CI command (`uv export --frozen --format requirements-txt --no-emit-project --no-hashes --all-extras | pip-audit -r - --ignore-vuln CVE-2025-69872`, pip-audit 2.10.1) was reproduced locally against that same unchanged lockfile and gave the identical result: **8 known vulnerabilities in 2 packages**. `main` itself carries this today — it just hasn't been scanned since, because this workflow only runs on PRs, not on push to `main`, and no PR has picked up a fresh scan since these CVEs were published.

- **`dnspython` 2.8.0** (transitive, via `email-validator`): CVE-2026-114605, fixed in **2.9.0**.

No existing PR or Dependabot run fixes this yet (checked open/closed PRs for `authlib`/`dnspython`; none found). The likely fix is `uv lock --upgrade-package authlib --upgrade-package dnspython` (assuming fastmcp's resolution range allows it) followed by the full test suite, in its own PR — not this one.
