**#313 — "[Feature]: add configuration to limit # of tools based on Canvas user role"**
(zqian, University of Michigan — high-priority external collaborator, owns #170/#172/#181;
1 comment from jonespm) — opened 2026-08-20T16:02:13Z, jonespm replied 2026-08-20T17:34:58Z.

zqian's problem: Azure's platform caps combined MCP tools at 128, and they need to run Canvas
MCP alongside other connectors, so they're asking for a `CANVAS_USER_ROLE` env var that filters
the tool list to student-facing or teacher-facing tools only. jonespm's reply raises a real
design wrinkle: role can be context-dependent (instructor in one course, student in another),
and a static role filter risks silently hiding tools a user actually needs; jonespm suggests
category-based grouping (pointing at `docs/llms.txt`) with a discovery mechanism that expands
tool groups by category instead.

**Checked the repo — this is already implemented and shipped.** `CANVAS_ROLE` exists today
(`src/canvas_mcp/core/config.py:277`, valid values `student`/`educator`/`all`) and gates tool
registration in `register_all_tools()` (`src/canvas_mcp/server.py:424-472`): student tools only
register when `role in ("student", "all")` (:447-451), educator tools only when
`role in ("educator", "all")` (:454-469). Documented in `AGENTS.md:31-36` with tool counts:
`CANVAS_ROLE=student` → ~37 tools, `CANVAS_ROLE=educator` → ~88 tools, `CANVAS_ROLE=all`
(default) → 94-99. Also settable per-invocation via `canvas-mcp-server --role student` (CLI
flag takes precedence over the env var). Both numbers comfortably clear the 128 combined-tool
cap zqian is hitting, even stacked with a few other connectors.

**Not fully solved:** jonespm's context-dependent-role point doesn't have an answer today — role
is fixed for the life of the server process (env var or CLI flag at startup), not adjustable
per-request or per-course. That matters more for the hosted/HTTP deployment (where a single
running instance serves many callers) than for the stdio/local case zqian's Azure combined-tools
problem sounds like it's describing.

Draft reply:
```
Good news: this already exists, and I think it solves your immediate 128-tool-cap problem as-is.
Set CANVAS_ROLE=student or CANVAS_ROLE=educator (env var, or --role on the CLI, which takes
precedence) and the server only registers that profile's tools at startup — about 37 for
student, 88 for educator, versus 94-99 unfiltered. Details in AGENTS.md. Can you try that and
let me know if it gets you under the combined 128-tool limit with your other connectors?

@jonespm's point is a real gap though: CANVAS_ROLE is fixed for the life of the process, so it
doesn't help if the same running instance needs to serve both an instructor-in-course-A and a
student-in-course-B. That's a different, harder problem than zqian's immediate ask (a static
per-deployment cap), and category-based dynamic discovery is one reasonable direction for it —
but I'd rather not conflate the two in one issue. zqian, if the static CANVAS_ROLE split doesn't
actually solve what you're running into, let me know what your deployment shape looks like
(one server instance per user? shared?) and I'll reopen the scoping question.
```

2026-08-20 brief) is unchanged and still accurate — it was simply never posted.

Draft reply:
```
Thanks for filing this with the payload example — that's helpful, and it's a real gap. The
closest thing today is canvas-course-builder's "clone from existing course" mode, but that only
recreates structure (module/page/assignment names) by reading one course and rebuilding items in
another — it explicitly doesn't copy content or use Canvas's own copy API. Nothing in the
codebase calls content_migrations.

Before I scope a tool, a few things I want to get right given the blast radius: a course copy is
a write into an existing target course, it runs async (Progress API polling, not a single
request/response), and depending on selective_import it can touch grading structure, due dates,
and existing content the target course already has. I'd want the tool to default to a
dry-run/preview of what would be copied, require explicit confirmation before the real migration
kicks off, and surface Progress API failures (partial imports, individual item errors) rather
than reporting bare "started" success.

Two questions that would shape the design: (1) do you need selective import (pick specific
assignments/discussions/etc.) from day one, or is "copy everything" enough for a first version
with selective import as a fast follow; (2) is date_shift_options a hard requirement for your
workflow, or can that wait? Selective import is the bigger lift of the two (Canvas's
copy-parameters format for choosing individual items is its own small API surface), so knowing
whether you need it now changes the estimate a lot.
```
