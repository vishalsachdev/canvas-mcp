### Correction 1 — #340's root-uid fix is incomplete (measured)

The brief says the blocking finding "is fixed" and that the PR "looks ready to merge" once green.
**It is not fully fixed.** The new guard in `config.py` compares *strings*:

```python
uid, gid = config.ts_sandbox_uid_gid.split(":")
if uid == "0" or gid == "0":
```

but the format gate in front of it is `^\d+:\d+$`, which accepts leading zeros. So `00` passes the
shape check and is not string-equal to `"0"`. Probed through the PR's own test harness
(`get_execute_typescript` + the same `create_subprocess_exec` patch the new test uses), reading the
effective `--user` argument:

```
input '0:0'       -> --user '65532:65532'   ok (rejected)
input '00:00'     -> --user '00:00'         >>> passes through <<<
input '0000:0'    -> --user '65532:65532'   ok (gid is literally "0")
input '00:65532'  -> --user '00:65532'      >>> passes through <<<
input '010:010'   -> --user '010:010'       passes through (uid 10, not root)
```

So `TS_SANDBOX_UID_GID=00:00` reaches Docker's `--user` unchanged. The fix catches the exact
literal AmirF194 reported and misses the trivially-adjacent forms.

**What I could not measure:** whether Docker resolves `--user 00:00` to uid 0. The `docker` CLI is
present in this sandbox but there is no daemon (`/var/run/docker.sock` absent), so the container
half is unverified here. Treat "`00:00` runs as root" as strong inference from Docker parsing the
field numerically, **not** as a measurement — the same standard the brief rightly applied to the
original finding before AmirF194 reproduced it.

The obvious fix is comparing numerically (`int(uid) == 0 or int(gid) == 0`) — but this is a fork PR,
so no code and no comment from me.

rejects "uid/gid 0 explicitly" and promises to resolve the thread once CI is green; both overstate
what the commit does. Resolving that thread on a green run would close a finding that is still
