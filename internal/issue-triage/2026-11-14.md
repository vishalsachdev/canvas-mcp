1. **#587's reported pre-existing failures do not reproduce here.** The PR body reports

   it does not hold up as stated.
2. **The brief's "`get_my_submission_status` already distinguishes these states for the
   same underlying data" is imprecise.** `get_my_submission_status` reads
   `/courses/:id/assignments?include[]=submission` and keys off
   `submission["excused"]` and `submission["workflow_state"] == "graded"`, and it has a
   fourth state, `NO ONLINE SUBMISSION REQUIRED`, for `on_paper`/`none` submission types.
   `get_my_upcoming_assignments` reads `/planner/items` and keys off a differently shaped
   embedded `submissions` object. Same *concept*, different endpoint and different field
   shape — so the fix is not a straight copy of an already-proven mapping.
3. **One claim in this chain remains unmeasured, and it is the load-bearing one.**
   Whether `/planner/items[].submissions` actually carries `excused` and `graded` boolean
   keys is live-Canvas behavior. Neither the triage agent, the contributor's tests (all
   payloads fabricated) nor this executor can measure it — the 5 new tests prove the
   mapping logic given those field names, not the field names themselves. If Canvas's
   Planner payload spells them differently, #587 is a no-op that still reports
   `❌ Not Submitted`. Worth one check against the Planner API docs or a real Planner
   response before merge.
