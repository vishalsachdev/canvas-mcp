**What happened first (context, not new):** you opened and merged PR #378 same-day, which fixed the

comments on both issues explaining the fix and asking whether either reporter could retest against a

**What chiptoe-svg said in the new comment:** first, a correction of their own initial report — it
was the README that called create/update "web-only," not a real capability gap, since `create_rubric`
already existed. Then, unprompted, they answered the open `update_rubric` design question by reading
`instructure/canvas-lms` (master) directly and found two hazards for any future update tool:
1. `Rubric#update_criteria` replaces the entire criteria/ratings array from the request. If an update
   omits a criterion's id, `unique_item_id` mints a fresh one (`"#{rubric_id}_#{rand(10000)}"`) rather
   than erroring — and since rubric assessments key scores by criterion id, that silently orphans
   existing grading data with no visible failure.
2. In `RubricsController#update`, if the caller lacks `:update` on the rubric, or the rubric's context
   is a different `Account` than the request context, Canvas builds and saves a **new** rubric
   (`@context.rubrics.build`) instead of updating the existing one — a `PUT` that quietly creates
   under those conditions rather than failing.

They're explicit both are source-read, not measured against a live Canvas instance, and that they
have no read-back example to offer since this project's tool doesn't do updates. There's no direct
ask — it's a contribution toward the open design question, not a bug report needing a fix.

**Draft reply:**
```
This is exactly the kind of research I was hoping for when I left that open — thank you. Both
hazards you found line up with why update_rubric has stayed out of scope rather than shipped
half-safe:

- The id-reuse issue is the sharper one. If an update has to echo back every existing
  criterion/rating id to avoid a silent re-key, that means update_rubric would need to fetch the
  current rubric first, merge the caller's changes into the full existing structure, and send the
  complete set back — never a partial diff. A tool that let a partial update through would silently
  orphan grading data with no error, which is worse than not having the tool at all.
- The build-a-new-rubric-instead-of-updating path (missing :update permission, or a cross-Account
  context) is a good example of exactly the kind of silent-wrong-thing this project's
  unconfirmed-write guards exist to catch. Any update_rubric implementation would need an explicit
  precheck for both conditions rather than trusting a 200 back.

No update/read-back example needed on your end — this source analysis is enough to scope it
properly whenever I get to building it. I'll fold both points into the design if/when update_rubric
happens. Appreciate you following through on this even without a live instance to test against.
```
