### ⚠️ #374 — `use_for_grading` silently decides whether writing a rubric assessment posts a grade
**@chiptoe-svg**, first-time reporter (`author_association: NONE`), opened 14:53:44Z. No comments
yet. High-sensitivity by policy (grading/rubric-write path).

**What they said:** They read Canvas's own source (`app/models/rubric_assessment.rb#update_artifact`)
rather than the docs, because neither `rubrics.html` nor `submissions.html` states what a rubric
assessment write does to the gradebook. Their finding: whether writing a `rubric_assessment` posts
a grade depends entirely on the *rubric association's* `use_for_grading` flag — if false, criteria
and comments save but the gradebook is untouched; if true, Canvas sums the criteria and grades the
student itself, with no `posted_grade` in the request. Two more undocumented gates: the assessor
needs the assignment's `:grade` right, and checkpointed assignments are excluded outright. They
flag this as a risk for "bulk rubric grading" specifically, in case a caller submits rubric
assessments without checking the flag first.

**Root-cause check against this repo (my own reading, unverified against a live Canvas, cite only)**:
this specific risk is already guarded against on both paths that write rubric assessments here.
`grade_with_rubric` explicitly checks `use_for_grading` and refuses with a clear "grades will NOT
be saved" error before submitting if it's false (`src/canvas_mcp/tools/rubrics.py:795-803`), and
`bulk_grade_submissions` does the identical check with the identical refusal, plus points at
`dry_run=True` (`src/canvas_mcp/tools/assignments.py:1049-1073`). This class of gap is what #235
(bulk-grading comment defaults) closed last month. So their finding is accurate about Canvas's
undocumented behavior in general, but doesn't describe a live bug in this server as far as I can
tell from the source — worth confirming rather than assuming, since I didn't run this against a
real Canvas instance.

**Draft reply:**
```
Thanks for going to the source on this — Canvas's own docs really don't say what a rubric_assessment
write does to the grade, and the four gates you found (use_for_grading, the :grade right, the

Good news on this specific risk: both of this server's rubric-grading paths (grade_with_rubric and
bulk_grade_submissions) already check use_for_grading before writing and refuse with an explicit
error if it's false, rather than silently storing criteria with no grade — that was tightened up in
```

### ⚠️ #375 — Rubric create/update does work over the REST API — the blocker is an undocumented request shape
Same reporter, **@chiptoe-svg**, opened 14:53:49Z (6 seconds after #374, cross-references it). No
comments yet. High-sensitivity by policy (rubric write path).

**What they said:** The README line that rubric create/update is "web-only due to API
constraints" overstates the problem — the endpoints work, but Canvas's docs never show a worked
request body for `rubric[criteria]`, only prose ("an indexed Hash... where the keys are integer
ids"). Sending criteria as a JSON array gets a bare HTTP 500. The fix is index-keyed hashes at both
the criteria and nested-ratings level. They also note `free_form_criterion_comments: false` reads
back as `null`, which can look like a write mismatch to anything that verifies by reading the
object back. They aren't opening a PR — their own implementation runs through a local guard
process that wouldn't port — but offered to answer questions.

**What I found reading this repo's own source:** this project's `create_rubric` already avoids the
exact trap they hit. `build_rubric_create_form_data` (`src/canvas_mcp/tools/rubrics.py:248-347`)
sends **form-encoded bracket notation** (`rubric[criteria][0][description]`,
`rubric[criteria][0][ratings][0][description]`, etc.), not a JSON array — which is precisely the
"index-keyed hash" shape Canvas wants; Rails/Rack parses bracketed form keys into exactly that
structure. So the specific failure mode in their report doesn't apply to `create_rubric` as
written, unverified against a live Canvas call only because I didn't make one.

**Separately, a doc inconsistency this made me notice (not something they reported):**
`README.md:525` still says *"Note: Create/update rubrics via Canvas web UI due to API
limitations,"* but `AGENTS.md:347` lists `create_rubric` as a working, shipped tool, and it has
been since #100 (v1.3.0). The README line reads like it predates that tool and was never updated.
The `update_rubric` gap is real but for a different, already-documented reason
(`AGENTS.md:345` — Canvas's `PUT` on a rubric is full-replacement, not a partial `PATCH`, so a
partial update silently wipes untouched criteria) — that's a design constraint, not a
request-shape problem, so #375 doesn't close it on its own.

**Correction (2026-09-14, post-review):** an earlier version of this section misidentified the
stale line as `AGENTS.md:525`; a `claude[bot]` review on this brief's own PR (#376) caught it —
`AGENTS.md` has no such line at all, only the accurate `update_rubric` caveat cited above. The
stale note is in `README.md`, corrected above.
