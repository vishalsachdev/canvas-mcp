### Root cause for #391 — the brief's hypothesis is close but not what the log says

The brief marked its Python-3.15-wheels theory as unverified because it had not read the attached log. The log is a public GitHub attachment and **was** fetchable, so it is now read. Treating its contents as reporter-supplied data, the failing step is:

- `Using CPython 3.15.0 interpreter at: C:\Users\dm\AppData\Local\Programs\Python\Python315\python.exe`
- `error: Failed to build cffi==2.0.0`
- `distutils.compilers.errors.PlatformError: Microsoft Visual C++ 14.0 or greater is required.`
- dependency chain in the log: `cffi (v2.0.0) was included because canvas-mcp (v1.14.0) depends on mcp (v2.1.1)` → `pyjwt[crypto]` → `cryptography` → `cffi`
- then `Server transport closed unexpectedly` / `Error: Connection closed`
- **no** `spawn uv ENOENT` anywhere; `C:\Users\dm\.local\bin\uv.exe` resolves fine, so the `uv`-on-PATH problem really is fixed and this is a separate build failure

So the proximate cause is not "3.15 is unclassified" in the abstract: `cffi==2.0.0` publishes no CPython 3.15 Windows wheel, `uv` therefore falls back to a source build, and the source build needs an MSVC toolchain the reporter does not have. The 3.14 classifier ceiling is the right thing to mention, but as the reason no one tested this path — not as the mechanism. **Corrected draft reply, replacing the one above:**

```
Glad the uv fix got you unstuck — and thanks for the log, it pins this
down exactly. This is a different failure, not a leftover of the first
one: your uv resolves fine, and nothing in the log is a PATH problem.

What happens is that uv has to build cffi 2.0.0 from source, because
cffi doesn't publish a Windows wheel for CPython 3.15 yet, and the
source build needs the Microsoft Visual C++ build tools, which aren't
installed on that machine:

    error: Failed to build cffi==2.0.0
    PlatformError: Microsoft Visual C++ 14.0 or greater is required.

cffi comes in transitively (mcp -> pyjwt[crypto] -> cryptography ->
cffi), so there's nothing you can do at our layer to avoid it on 3.15.
Two ways out, easiest first:

1. Install Python 3.13 or 3.14 alongside 3.15 and point the extension at
   it. Those have prebuilt cffi/cryptography wheels, so nothing compiles.
   This is the one I'd do.
2. Or install the "Desktop development with C++" workload from the
   Microsoft C++ Build Tools, which lets the source build succeed.

To be straight with you about support: pyproject.toml declares
requires-python >=3.11 and classifies up to 3.14, so 3.15 isn't a tested
configuration yet. That's on us to catch at install time rather than
leaving you to discover it from a compiler error.

On your process question — you're right, and this is a good example. The
installer should check the interpreter version against what we actually
support and say so up front instead of dropping into a C build. I'm
taking that as the concrete ask for hardening the .mcpb packaging.
```
