### #351 in detail (new)

Opened 2026-09-04T21:55:05Z by **bruchris**, who says in the PR body they maintain a different
Canvas LMS MCP server and found this while reading our code-API discovery path — appears to be a
first-time contributor here. Small, well-scoped, high-confidence fix:

- **Bug:** `search_canvas_tools` (`src/canvas_mcp/tools/discovery.py:130,145,162`, three call
  sites) reads bundled `code_api/**/*.ts` files with `Path.read_text()` and no explicit encoding,
  so decoding falls back to the host locale. Two files (`grading/bulkGrade.ts`,
  `discussions/bulkGradeDiscussion.ts`) contain `✓`/`✗` in console-output strings; on a
  non-cp1252/non-UTF-8 Windows code page (their repro table lists cp932 Japanese, cp936
  Simplified Chinese, cp1253 Greek) that raises `UnicodeDecodeError`. The content-search branch
  swallows it in a bare `except Exception: continue`, so the two files silently vanish from
  results with no error surfaced — `entries_with_error` stays `0`.
- **Fix:** pins `encoding="utf-8"` on all three reads (the files are UTF-8 on disk; this is a
  one-word-per-call-site change, +64/-3 across 2 files). Confirmed `execute_typescript` itself is
  unaffected — it runs the files through Node, not this Python read path.
- **Tests:** two new tests in `tests/tools/test_discovery.py` with a `monkeypatch` fixture that
  makes encoding-less reads resolve to cp932, so the tests actually exercise the bug on UTF-8 CI
  (verified both ways: `2 failed, 13 passed` before the fix, `15 passed` after — the PR body
  states this explicitly).
- I read the diff directly rather than only the description — the fix is exactly what the PR body
  claims: three `read_text()` calls gain `encoding="utf-8"`, nothing else touched. No FERPA/data
  angle (static bundled TypeScript source, not Canvas or student data).
