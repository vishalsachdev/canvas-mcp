### #252 ⚠️ — created announcement was not saved in Canvas
Filed by **zqian** (external collaborator), 2026-08-08 15:36 UTC, v1.6.0 / Claude Desktop
macOS. `create_announcement` reported success and returned an announcement ID, but the announcement never
appeared in the Canvas course site, wasn't retrievable by ID afterward, and didn't show up in a raw Canvas API
listing either. Not 100% reproducible — happened "multiple times." No comments yet.

**Unverified analysis** — `create_announcement` (`discussions.py:968-999`) POSTs a plain **JSON** body
(`data=data`, no `use_form_data=True`) to `/courses/{id}/discussion_topics` with `is_announcement: True`. There's
already a guard for a *related* but different failure mode: `discussions.py:1010-1027` checks whether the
response actually echoes `is_announcement: true` and returns an explicit "unconfirmed write" warning instead of
claiming success if it doesn't (added for #220, where Canvas silently drops the flag when the token lacks
announcement permission). zqian's report describes the tool returning the plain success message
(`discussions.py:1029`), meaning that guard did **not** trigger — so if the root cause is what PR #253 (below)
proposes, it's a step worse than #220: Canvas is apparently echoing `is_announcement: true` back in the
immediate POST response without actually persisting the topic as a real, listable announcement, which would
defeat the existing guard entirely since it only checks the echo, not a follow-up read. This project has hit
this general shape of Canvas quirk before (JSON vs. form-encoded booleans not being honored reliably — see
`discussions.py:154` area for `#207`, and `#210`/`#220` for the same tool family), so the theory is plausible,
but unconfirmed without reproducing against a live instance.

**Community fix already proposed:** PR #253 (external, first-time contributor) switches this POST to
`use_form_data=True`, citing the same mitigation used in #210. Worth testing rather than writing from scratch —
see PRs section above.
